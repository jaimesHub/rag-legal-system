# T0 — Skeleton repo, Docker Qdrant, lớp abstraction, smoke test

> Tham chiếu: `docs/plan.md` §1 (quyết định chính), §1b (chỗ ghi kết quả xác nhận dữ liệu),
> §3 (T0 trong lộ trình 8 tuần), §5 (cấu trúc repo). File này là checklist hành động —
> không phải code — để dựng T0 từ một repo trống.

**Câu hỏi của tuần:** pipeline end-to-end (dataset → chunk → embed → Qdrant → retrieve →
metric) có chạy được bằng **một lệnh**, và dataset có đúng như plan giả định không?

## 🎯 Mục tiêu

Dựng đủ khung để lần đầu tiên có một con số benchmark (dù chỉ là regression tripwire, chưa
phải baseline chất lượng), chạy 100% offline (không cần `GEMINI_API_KEY`), và xác nhận 4 giả
định về dataset trong plan §1 bằng dữ liệu thật (ghi kết quả vào §1b).

- [ ] Skeleton repo đúng cấu trúc plan §5 (`config/`, `src/`, `data/`, `tests/`, v.v.)

## Thứ tự thực hiện

Nguyên tắc dựng: **config trước, contract trước implementation, ingest trước index, index
trước retrieve, retrieve trước eval, CLI nối sau cùng** — mỗi lớp chỉ phụ thuộc lớp trước nó,
không phụ thuộc ngược. Đây là thứ tự suy ra từ kiến trúc `src/` trong dự án mẫu (ingest →
index → retrieve → eval, đúng như sơ đồ pipeline ở plan §2), không phải từ lịch sử commit
chi tiết — ở dự án mẫu, toàn bộ T0 nằm trong **một** commit lớn thay thế hoàn toàn scaffold
ban đầu, nên không có "vết" từng bước nhỏ để noi theo; thứ tự dưới đây được suy ngược từ phụ

### 6. `src/providers/` — lớp abstraction (plan §1)

- `base.py`: hai `Protocol` — `EmbeddingProvider.embed(texts, task_type) -> vectors`,
  `LLMProvider.complete(prompt)` / `.judge(rubric, sample)`. `TaskType` là Literal
  (`RETRIEVAL_DOCUMENT` / `RETRIEVAL_QUERY` / `SEMANTIC_SIMILARITY`) — encode bất đối xứng
  query vs document.
- `fake.py`: `FakeEmbeddingProvider` — hash bag-of-words xuống đúng `dim`, chuẩn hoá L2,
  **tất định** (cùng input → cùng output mọi lần chạy); `FakeLLMProvider` echo + judge giả
  tất định. Mục đích duy nhất: chạy toàn bộ pipeline **không cần mạng, không cần API key,
  không tốn tiền** để smoke test và test suite.
- `gemini.py`: `GeminiEmbeddingProvider` gọi `google-genai`, retry qua `tenacity` (chỉ retry
  lỗi transport/quota, lỗi request sai phải fail ngay); xử lý 2 khác biệt giữa các model
  embedding — (a) `task_type` chỉ một số model chấp nhận, model khác thì chèn task hint vào
  đầu text; (b) phải wrap từng input thành `Content` riêng, nếu không API gộp cả batch thành
  1 vector duy nhất. `GeminiLLMProvider` cho `complete`/`judge`.
- `registry.py`: `get_embedding_provider(settings)` / `get_llm_provider(settings, role=...)` —
  **một chỗ duy nhất** map config → implementation; `role="judge"` dùng model khác
  `role="generator"` để giảm self-preference bias (chuẩn bị cho T1, chưa cần dùng ở T0).

**Verify:** chạy `FakeEmbeddingProvider(dim=128).embed(["a", "b"], "RETRIEVAL_QUERY")` ra 2
vector cùng norm ~1.0; `get_embedding_provider(Settings(provider="fake"))` trả đúng type.

### 7. `src/ingest/loader.py` — tải dữ liệu thật + `make verify`

Đọc thẳng JSONL gốc trên HuggingFace (`hf_hub_download`, revision pin), **không** qua thư
viện `datasets`/config MTEB — vì file gốc mang cả `qrels/train.jsonl` (config MTEB chỉ expose
`test`) và dùng khoá `_id` (config parquet dùng `id` — loader phải nhận cả hai). Một hàm
`_download` dùng chung cho mọi loader nên **không cần bước tải tay riêng** — lệnh đầu tiên
cần dữ liệu sẽ tự tải vào `data/raw/` (git-ignored) và cache lại.

Khai báo hằng số `EXPECTED` (số liệu kỳ vọng sẽ đối chiếu — corpus records, query rows/unique,
qrels train/test labels & query counts, overlap) và implement lệnh CLI `verify-dataset`: tải
`corpus.jsonl`, `queries.jsonl`, `qrels/train.jsonl`, `qrels/test.jsonl`, in bảng
expected-vs-observed, log số dòng trùng trong `queries.jsonl` và số query id giao nhau giữa
train/test qrels.

**Đây là bước quan trọng nhất để verify 4 giả định của plan §1b** — chạy xong, điền kết quả
thật vào `docs/plan.md` §1b (không làm ở T0 guide này, làm khi báo cáo T0 xong):
1. Corpus đã chunk sẵn ở mức Điều hay chưa (kiểm tra vài id mẫu)
2. Trung bình bao nhiêu nhãn/câu — có phải hầu hết binary/1-nhãn không
3. Có leakage query id giữa train/test qrels không, bao nhiêu id
4. `queries.jsonl` có dòng trùng `_id` không, bao nhiêu

**Verify:** `make verify` (sau khi thêm target Makefile) chạy xong không lỗi mạng; bảng
expected-vs-observed toàn "yes" hoặc in rõ chỗ lệch (nếu pin dataset đã trôi thì đây là nơi
phát hiện sớm nhất, trước khi ảnh hưởng ingest).

### 8. `src/ingest/clean.py`, `metadata.py`, `chunk.py`

- `clean.py`: chuẩn hoá NFC + dọn whitespace cho `title`/`text`.
- `metadata.py`: `parse_corpus_id("01/2009/tt-bnn+1")` → tách `doc_key` / `article_index`;
  `doc_key` tách tiếp `number/year/code`; `code` suy ra `doc_type` (thông tư, nghị định, luật,
  …) + `issuer`; trường hợp riêng của Quốc hội (`qh14` là khoá quốc hội, không phải issuer).
  Parse **phòng thủ** — id không khớp format thì set `parse_ok=False`, đếm lại trong audit,
  **không raise** (một id lỗi không được phép làm sập cả lượt ingest). `parse_title` lấy số
  Điều + tiêu đề từ chuỗi title dạng "Điều 15. Xử phạt...".
- `chunk.py`: `chunk_document(corpus_id, title, text, settings)`. Chiến lược mặc định
  `"article"` — **giữ nguyên đơn vị record** (corpus đã ở mức Điều, xem bước 7) vì golden
  label trỏ đúng vào record đó; đơn vị nhỏ hơn sẽ không còn khớp 1:1 với nhãn. Chiến lược
  `"khoan"` cắt theo Khoản (regex đầu dòng `"1."`, `"2."`, …), gộp segment quá ngắn vào đoạn
  trước, và cắt tiếp theo Điểm (`"a)"`, `"b)"`) hoặc cắt cứng theo `chunk_max_chars` nếu đoạn
  vẫn quá dài — nhưng **`doc_id` luôn trỏ về Điều cha** để metric vẫn so sánh được giữa hai
  chiến lược. `embed_text` = tiêu đề + nội dung (tiêu đề thường mang tín hiệu mạnh nhất cho
  câu hỏi kiểu tra cứu).

**Verify:** unit test cho vài corpus id mẫu (đúng format, sai format, format Quốc hội); chunk
một Điều dài giả lập vượt `chunk_max_chars` ra đúng số mảnh mong đợi.

### 9. `src/eval/golden.py` + `make golden`

`build_golden(settings)`: load queries (dedupe theo `_id`, log số dòng trùng), load qrels
train + test, tính giao `train.query_ids & test.query_ids` (leakage) → loại các id đó khỏi
**dev** (từ qrels train), **giữ nguyên trong test** — vì bất cứ thứ gì train trên dev sau này
(vd. fine-tune embedding) sẽ không thể đã thấy một câu test. Ghi `data/golden/dev.jsonl`,
`test.jsonl`, và `manifest.json` (đếm nhãn/câu, số multi-label, danh sách id bị loại — để
audit được, không chỉ tin vào log). `load_golden(settings, split)` đọc lại.

**Verify:** `make golden` → bảng thống kê dev/test (số câu, nhãn/câu, multi-label, excluded);
unit test khẳng định id trùng bị loại khỏi dev nhưng **vẫn còn** trong test.

### 10. `src/ingest/pipeline.py` — slice "gold-covering" cho smoke + `make ingest`

`build_passages(settings, limit, gold_doc_ids)`: stream corpus một lượt, chunk từng record,
gom audit (số Điều, số passage, phân bố ký tự, số lỗi parse metadata, phân bố loại văn bản,
khoảng năm). Với `limit` (T0 dùng 500), slice **phải cố tình bao phủ vàng**: ép các gold
document của một số câu golden vào trong slice trước, phần còn lại lấp bằng tài liệu tiếp
theo trong file làm distractor (`plan_gold_coverage`). Lấy 500 tài liệu đầu file theo thứ tự
tự nhiên gần như không câu nào có đáp án nằm trong index → mọi metric ra 0.00, smoke test
không chứng minh được gì. **Ghi rõ trong docstring** rằng con số ra từ slice này là optimistic
by design, không phải chất lượng thật (số thật full-corpus chờ đến T3).

`write_passages`/`load_passages` ghi/đọc `data/processed/passages.jsonl` +
`ingest_audit.json`.

**Verify:** `make ingest LIMIT=500` → bảng audit in ra (documents, passages, chars mean/max,
metadata parse failures, gold docs found/x, year range); `gold docs found` phải bằng đúng số
gold id đã ép vào.

### 11. `src/index/qdrant_store.py` + `make index`

`QdrantStore`: collection dùng **named dense vector** (`"dense"`) ngay từ đầu — Qdrant không
thể thêm named vector vào collection đã tồn tại, nên đặt tên trước để T4 (sparse vector) chỉ
cần thêm, không phải viết lại. Point id = UUID5 tất định từ `passage_id` (khoá tự nhiên là
string, Qdrant cần uint64/UUID) — nhờ vậy chạy lại lệnh index là **upsert đè**, không tạo
trùng. Payload index tạo sẵn cho các field T5 sẽ filter (`doc_id`, `doc_key`, `doc_type`,
`issuer`, `year`) dù chưa filter gì ở T0. `ensure_collection(recreate=...)`, `upsert`,
`search`, `count`, `collection_info`, `iter_payloads` (scroll toàn bộ payload — dùng ở T2 để
dựng BM25 từ dữ liệu đã index).

**Verify:** `make index` → in số điểm đã upsert, `collection_info()` khớp số passage đã
ingest; mở `localhost:6333/dashboard` thấy đúng số point.

### 12. `src/retrieve/base.py` + `vector.py`

`base.py`: contract chung `Retriever.retrieve(query, k) -> list[SearchHit]`, `SearchHit`
(doc_id, score, passage_id, title, text, metadata), `dedupe_by_doc` (nhiều passage/chunk của
cùng 1 Điều không được chiếm hết top-k — gom về theo `doc_id`, giữ điểm cao nhất).

`vector.py`: `VectorRetriever` — embed query với `task_type="RETRIEVAL_QUERY"` (bất đối xứng
với `RETRIEVAL_DOCUMENT` lúc index), gọi `QdrantStore.search`, oversample `k×3` trước khi
dedupe theo document (nếu không, top-k có thể toàn passage của 1-2 Điều).

**Verify:** `make search Q="..."` ra bảng kết quả có điểm giảm dần, không có `doc_id` trùng.

### 13. `src/eval/metrics.py` + `harness.py`

`metrics.py`: `metrics_at_k(ranked, relevance, k)` — Recall, Precision, MRR, nDCG, MAP,
hit_rate tại từng k; `aggregate(runs, qrels, ks)` macro-average qua toàn bộ query.

`harness.py`: `evaluate_retriever(retriever, examples, ks, split, ...)` chạy từng query, đo
latency per-query (không chỉ tổng), gom **per-query** (không chỉ aggregate — số tổng hợp có
thể che mất việc một nửa số câu tốt lên trong khi nửa kia tệ đi, bài học sẽ rõ hơn ở T2) vào
`QueryResult`, tính `run_id` tất định từ (retriever, split, context) để nhận ra hai lần chạy
có phải cùng cấu hình. `EvalReport` gồm metrics, latency (mean/p50/p95), `failures` (danh sách
miss tệ nhất), toàn bộ `per_query`, và `context` (provenance: dataset revision, chunk
strategy, provider, embed model/dim, collection — để report tự giải thích được nó sinh ra từ
đâu). `save_report`/`load_report`/`list_reports` ghi JSON vào `artifacts/eval/`.

**Verify:** unit test cho `metrics_at_k` với vài trường hợp tay (hit ở rank 1, hit ở rank k,
miss hoàn toàn); `evaluate_retriever` trên 2-3 query giả cho ra đúng `n_queries`, latency > 0.

### 14. `src/cli.py` — ráp toàn bộ thành lệnh

Typer app, các lệnh **cần cho T0** (chưa thêm `tokens`/`sweep`/`compare`/`view-eval` — những

`_embedder(settings)` resolve provider qua registry, fail với message rõ ràng (không phải

### 16. `tests/`

`conftest.py`: fixture `settings` dựng `Settings(base_dir=tmp_path, provider="fake",
embed_model="fake-embedding", embed_dim=128, _env_file=None)` — **`base_dir` là điều kiện bắt

## Bẫy cần tránh (rút ra từ dự án mẫu — kiểm tra chủ động, đừng đợi tự lộ ra)

1. **Test suite ghi vào repo thật.** Nếu `Settings` derive path từ hằng số tính lúc import
   (`Path(__file__).parents[1]`) thay vì từ field `base_dir`, thì `monkeypatch.chdir(tmp_path)`
   trong test **không có tác dụng gì** — file test vẫn rơi vào `data/golden/`,
   `data/processed/` thật. Luôn cho `base_dir` là field của `Settings`, mọi path khác
   (`raw_dir`, `processed_dir`, `golden_dir`, `artifacts_dir`) là property derive từ nó, và
   fixture test luôn truyền `base_dir=tmp_path`.
2. **Vector giả lẫn vào collection thật.** Tên collection derive từ `embed_model` + `dim`.
   Nếu chạy `PROVIDER=fake` mà quên đổi `EMBED_MODEL`, vector hash sẽ ghi đè đúng UUID5 vào
   collection mà lần chạy Gemini thật sẽ dùng — không lỗi, không cảnh báo, chỉ âm thầm trộn
   hai loại vector khác hẳn nhau về ngữ nghĩa. Bắt buộc: khi `provider == "fake"`, tên
   collection phải dùng một model-slug khác hẳn (`fake-embedding`), không phải
   `settings.embed_model`.
3. **`k` lớn hơn corpus / query không khớp token nào trả về kết quả "trông bình thường".** Áp
   dụng cho T0 ở mức nhỏ hơn (BM25 chưa có), nhưng nguyên tắc chung: khi bọc bất kỳ thư viện
   retrieval nào, luôn tự hỏi "nó trả về gì khi không tìm thấy gì?" trước khi tin số liệu.
4. **Slice nhỏ ẩn luôn một lớp lỗi, không chỉ làm số liệu lạc quan.** Ví dụ, 173/61.425
   (~0.3%) corpus id không khớp format metadata chỉ lộ ra ở quy mô đầy đủ — trên slice 500 có
   thể là 0. Đừng kết luận "metadata parser ổn" chỉ vì audit ở slice nhỏ sạch sẽ.
5. **Điều luật dài bị cắt âm thầm khi embed thật.** `PROVIDER=fake` (hash embedder) không có
   giới hạn token nên lỗi này **chưa biểu hiện** ở T0, chỉ mới **đo được** qua audit độ dài ký
   tự. Nó sẽ biểu hiện ngay khi bật Gemini thật ở T1/T3 — đo trước bằng cách log phân phối độ
   dài passage (p50/p90/p99/max) trong `ingest_audit.json` ngay từ T0, đừng đợi đến lúc gọi
   API thật mới phát hiện.
